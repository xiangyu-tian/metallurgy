- 输入：`把100摄氏度换算为开尔文`
- 指定工具：A001
- 编排 ID：`ORCH-1CCEA0CEEA08E298`

### T04：多工具规划

### T07：同一函数重复步骤

- 输入：分别把 `100 °C` 和 `0 °C` 换算为 K，两步都要求执行 A001。
- 计划：`S1:A001`、`S2:A001`。

- 返回：`373.15 K`、`273.15 K`。
- 结论：复杂计划允许同一函数多次出现，步骤身份由“尚未消费的同名计划步骤”顺序绑定。

### T08：部分完成与同一编排恢复

- 第一轮输入：先用 A002 解析 `Fe2O3`，再执行 A001 温度换算；第二步参数稍后补充。
- 第一轮状态：`partially_completed_waiting_for_input` / `partially_completed`。
- 编排 ID：`ORCH-E0236C7B0D03653E`。
- 第一轮结果：A002 成功，S2 保持 pending；产品视图明确追问第二项输入。
- 第二轮输入：`数值100，源单位摄氏度，目标单位开尔文`，携带原编排 ID。
- 第二轮状态：`success`，编排 ID 仍为 `ORCH-E0236C7B0D03653E`。
- 最终成功步骤：`S1:A002`、`S2:A001`；A002 没有重复执行。
- 结论：候选集、计划和已完成记录均被保留，补参只推进未完成步骤。

### T09：产品结果与实验审计隔离

- `product_view`：只含业务结论、必要追问和简要警告。
- 实验审计：保留编排 ID、执行 ID、工具版本、输入参数、参数来源、真实返回和数据来源。
- 实测：重复工具链和部分完成续跑的产品视图均未出现 `A001/A002`、`EXEC-*`、编排或调用过程；对应审计绑定完整保留。
- 安全兜底：即使模型原始总结主动输出执行 ID，或数值漂移检查触发受约束重写/可读摘要，产品视图也不会泄露轨迹或原始 JSON。

### T10：参数来源校验

- 参数允许来源：当前/历史用户输入、Schema 显式默认值、前序成功工具结果。
- 反例：用户输入 `1000`，模拟模型生成 `100`；即使参数对象通过 Schema，也会因值没有可验证来源而停止执行并追问。
- 结论：校验已从“结构正确”扩展为“结构正确且每个非默认参数可追溯”。

### T11：数值漂移后的受约束模型重写

- 复现输入：`把25摄氏度换算成开尔文`，强制使用 A001，生产候选集。
- 根因：首次模型归纳提到了工具证据中不存在的关系常数，数值安全门将其识别为无依据数值；旧实现随后把完整 JSON 结果直接放进产品答案。
- 修复：保留安全门，改为把已验证工具结果再次交给模型，要求仅使用问题与工具证据中的数值生成自然语言结论。
- 真实接口回归：`answer_mode=tool_grounded_retry`，产品内容为“25摄氏度等于298.15开尔文……”；首次无依据值为 `273.15`，重写后最终无依据值为空。
- 结论：工具结果经过模型组织后再进入产品视图，没有直接显示原始 JSON。

### T12：模型重写失败时的可读降级

- 故障条件：模拟受约束重写服务不可用。
- 实际模式：`readable_tool_fallback`。
- 实际产品内容：按字段生成可读摘要，例如 `value：373.15`。
- 断言：不包含 JSON 代码块、花括号、工具编码、执行 ID 或调用过程。
- 结论：模型不可用时仍保留真实结果，但不会把机器 JSON 当作最终用户答案。

### T13：嵌套自然语言参数来源

- 输入：钢液1000 kg、Mn初始0.5 wt%、目标1.0～1.1 wt%，并明确给出FeMn80的成本、上下限、成分、收得率和质量保留率。
- 复现：模型生成的D019参数结构和值全部正确，但旧来源检查还要求用户原文包含`min_wt_pct`、`cost_per_kg`等内部Schema键名，因而误报`targets/alloys`无来源。
- 修复：递归校验时，Schema声明的结构键自动视为结构信息；元素名、合金名和所有业务值仍须来自用户输入或前序工具结果。
- 反向验证：将模型生成的合金成本从用户给出的2改成3时，来源闸门仍拒绝执行。
- 真实接口回归：D019成功执行，`targets`和`alloys`均绑定`user_input`。

### T14：模型答案中的合理舍入

- 工具真实结果：加入量`7.04225352112676 kg`、总成本`14.08450704225352`。
- 旧行为：模型写成`7.04 kg`和`14.08`时被误判为数值漂移，产品答案退化为完整字段摘要。
- 修复：仅对工具答案启用“由答案显示精度决定”的半单位舍入容差；整数粗化、明显篡改和新派生值仍不允许。
- 回归：`7.04/14.08`通过；`7.4`以及从目标区间自行计算出的`1.05`仍被拒绝。
- 真实产品答案：自然语言给出加入量、成本、终态质量和Mn含量，无原始JSON。

### T15：自然语言数值格式等价

- 输入：D018三段供氧优化完整参数，其中中期氧利用率写作`0.90`。
- 复现：模型正确生成数值`0.9`，旧来源检查按字符串匹配，错误地将整个`stages`标记为无来源。
- 修复：自然语言来源中的数字先规范化后按数值等价比较，同时支持常见科学计数写法。
- 防回归：`0.90`等价于`0.9`，`1×10^12`等价于`1000000000000`，但`100`不等价于`1000`。
- 真实接口回归：D018成功执行，三段参数来源均通过，返回总时长`5.4 min`的离线方案并声明不下发设备。

### T16：传统Tool Use默认基线与证据增强干预

- 新请求字段：`parameter_validation_mode=traditional|evidence_enhanced`。
- 默认值：`traditional`；只以候选权限、JSON、Schema及工具业务校验阻断执行。
- 审计行为：传统模式仍计算并记录`parameter_provenance`，但`unverified`不阻断，便于直接测量模型猜参率。
- 干预行为：显式选择`evidence_enhanced`后，无来源参数以`PROVENANCE_VALIDATION_FAILED`停止并追问。
- 研究设计：现有120个策略运行体固定为传统基线；RQ3复制同一运行体，只改变参数校验策略做配对比较。

### T17：D022物料衡算候选与结果归纳

- 输入：铁水90000 kg、Fe=0.94，废钢10000 kg、Fe=0.98，出钢92000 kg、钢水Fe=0.995，炉渣5000 kg、Fe=0.35，粉尘1000 kg、Fe=0.5；要求钢水收得率、铁回收率及铁损。
- 候选根因：D022注册类别为“冶金工艺与物料衡算”，旧converter场景白名单缺少该类别，导致专用工具在模型筛选前被排除，只剩D021/D014。
- 候选修复：补齐场景分类别名；真实重测候选顺序为D022、D021、D014，自动模式实际只执行D022。
- 归纳根因：工具返回比例`0.92`、`0.969703…`，模型按业务表达写成`92%`、`96.97%`时被旧数值闸门误判；重写稿中的少量额外推导又使整篇降级。
- 归纳修复：支持比例与百分数等价及显示精度舍入；问题文本在受约束重写时移除数值证据；仅删除仍含未绑定数值的局部分句，然后重新校验全文。
- 真实接口回归：D022执行成功，产品答案给出钢水质量收得率92%、铁回收率96.97%、炉渣/粉尘/未查明铁损，`unsupported=[]`、`warning=null`。

### T18：F005到F006的真实依赖链

- 原第14题错误地指定`F005_ANALYTIC_CONSTANT_V1`纯导热数学基准，却要求其产出中心固相率曲线；真实输出全部为`null`且`not_applicable_no_phase_model`，因此不能作为F006输入。
- 安全行为：编排层保留F005成功记录、拒绝补造固相率，状态为`partially_completed_waiting_for_input`；追问字段只保留真实缺失的`center_solid_fraction_curve`。
- 题目修正：改用批准的`NIST_SRM1155A_316L_2019_V1`验证物性集，半厚0.005 m、初温1750 K、恒定表面温度1500 K、时长10 s并输出21点曲线。
- 真实接口回归：F005与F006依次成功，中心固相率0.8对应时间约2.965 s、位置约0.0593 m，位于0.2 m有效冶金长度内。
- 产品视图修复：过滤中英文自我推演，不显示执行轨迹；短工具编码不再破坏`F005_ANALYTIC_CONSTANT_V1`等业务记录ID，脱敏后不残留空执行ID或空括号。

### T19：多工具依赖的结构化结果绑定

- 人工复现：F005已返回覆盖0～10 s的21点`time_history`，执行模型偶发只把阈值附近的曲线前缀传给F006，导致`MISSING_DATA`；随后又把配置名中的`020M`误读为20 m。
- 根因：编排层虽然把上游结果作为`tool`消息交给模型，但下游参数仍依靠模型重新复制大数组，完整性没有由系统保证。
- 修复：计划步骤存在显式依赖时，编排层按下游数组项Schema从上游结果投影完整对象数组；模型提供的是其有序子集时，用完整真实结果替换，并由系统写入真实`upstream_execution_id`。
- 审计：调用记录新增`dependency_bindings`，记录绑定字段、来源步骤、来源执行ID、来源路径、策略和数组点数。
- 真实接口复核：同一题F005→F006成功，终点约2.965 s、0.0593 m；批准验证设备有效冶金长度为0.20 m，出口时刻10 s。

### T20：元工具目标与内部参数契约

- 输入：问题28，要求对G008规则表线性插值模型的`query_x`做256次均匀采样，并统计输出分位数与失效概率。
- 初次失败：模型把函数语义别名`interpolate_lookup_table`写入`target_model_code`，该值虽满足旧Schema的字符串类型，却不是注册表中的模型代码，G010以`MODEL_NOT_APPLICABLE`拒绝。
- 间歇失败：目标代码修正后，模型又偶发漏掉`base_arguments.query_x`，或把相对路径写成`base_arguments.query_x`；旧元工具Schema只声明自由对象/自由路径，错误直到G010业务校验阶段才暴露，并被误转成面向用户的缺参追问。
- 修复：编排层按本轮候选动态枚举合法目标代码；唯一目标为G008时，让G010的`base_arguments`继承G008完整Schema，并把`uncertain_parameters[].path`枚举为目标Schema的数值字段路径。占位缺失或路径格式错误只允许模型在执行前受控修正一次。
- 结果归纳：强化主回答和受约束重写提示，要求逐项回答用户请求的指标；“122/256次失效”不能代替直接给出失效概率。进一步修复数值证据提取：直接遍历结构化结果，避免把Wilson区间数组的JSON逗号误作千位分隔符，并支持仅在区间一端书写百分号，防止概率与置信区间整段被误删。

## 测试中发现并修复的问题

首次运行 T01 时，强制模式使用 API 级 `tool_choice`，模型被迫生成工具调用并猜测为 `kg → t`。根因是“强制选择工具”错误等同于“无条件强制立即调用”。

修复后：

- 强制模式仍只暴露用户指定工具；
- 参数充分时必须调用；
- 参数不足时允许模型停止并追问；
- 没有执行记录时返回结构化 `needs_clarification`；
- 新增回归测试验证不再由 API 级强制调用迫使模型猜参。

新增修复还包括：

- 为每个参数记录 `user_input`、`schema_default`、`tool_result` 或 `unverified` 来源；
- 返回 `partially_completed_waiting_for_input`，避免把未完成链误标为成功；
