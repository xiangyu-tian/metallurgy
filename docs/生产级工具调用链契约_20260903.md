# 生产级工具调用链实验契约

版本：`production-tool-orchestration-v7`

本契约只定义 120 项工具之上的调用编排层；工具注册、Schema、资格门槛和底层执行接口保持不变。当前阶段仅接入实验平台 `/experiments/tool-calling`，正式聊天页 `/chat` 保持现有界面和调用逻辑，待实验验收后再迁移。

## 功能模块

| 模块 | 后端接口单元 | 前端交互单元 | 状态 |
|---|---|---|---|
| 候选筛选 | 从合格注册表按问题和场景筛选候选 | 显示候选数量、候选工具与选择依据 | 本次建设 |
| 调用策略 | 强制调用、自动选择、多工具规划 | 模式、场景、强制工具与研究模式控件 | 本次建设 |
| 参数闸门 | 在执行前按工具 JSON Schema 校验 | 显示缺失/错误字段并等待用户补充 | 本次建设 |
| 依赖绑定 | 按下游 Schema 从前序真实输出投影完整参数并绑定真实执行ID | 审计中显示字段、来源步骤与来源路径 | 本次建设 |
| 结果归纳 | 工具结果作为 `tool` 消息回传大模型 | 展示模型基于真实结果生成的答案 | 本次建设 |
| 执行审计 | 生成编排 ID、执行 ID、版本、参数和来源绑定 | 显示“选择—输入—返回—依据”证据卡 | 本次建设 |
| 规模研究 | 显式 `research_full` 才向模型暴露全量工具 | 研究模式开关及暴露数量提示 | 本次建设 |

## 冻结资格目录

实验平台读取`GET /api/v1/experiments/tool-registry`，执行时调用`POST /api/v1/experiments/tools/{function.name}/call`。两者复用现有注册模型和`ModelExecutionService`，但资格来源固定为`TOOL-ELIGIBILITY-20260903-120`快照，不调用`qualification_report`或`eligibility_report`，因此不会在实验服务启动或读取目录时重跑既有工具样例。

快照同时锁定`model_code`、`function.name`和`model_version`。注册数量、函数名或版本发生变化时，实验目录返回`TOOL_ELIGIBILITY_SNAPSHOT_INVALID`，要求先做重新验收和更新快照，不能静默沿用旧资格。正式`/api/v1/tools`及其动态资格逻辑不受本实验入口影响。

## POST /api/v1/experiments/tool-orchestration

工具调用实验台专用入口。该接口不挂接正式聊天页；本地开发默认由独立实验后端 `3001` 提供，前端使用当前页面主机名动态构建地址。

请求：

```json
{
  "message": "计算问题或自然语言任务",
  "history": [{ "role": "user", "content": "..." }],
  "orchestration_id": null,
  "mode": "auto",
  "scene": "thermodynamics",
  "catalog_mode": "production",
  "parameter_validation_mode": "traditional",
  "strict_tool_schemas": false,
  "forced_tool": null,
  "max_candidates": 12,
  "max_tool_calls": 4
}
```

约束：

- `mode`：`forced | auto | plan`。强制和自动模式最多执行一个工具；规划模式最多执行六个，默认四个。
- `catalog_mode`：默认 `production`，只向执行模型暴露候选集；`research_full` 是显式研究开关，保留 30/60/100+ 和全量 120 工具实验能力。
- `parameter_validation_mode`：默认 `traditional`，只用候选/权限、JSON、Schema和工具业务规则阻断；`evidence_enhanced` 额外用参数来源校验阻断，作为RQ3研究干预。
- `strict_tool_schemas`：是否请求供应商原生 Strict Schema。只有当前供应商端点与工具结构同时兼容才启用；不兼容时不改变业务 Schema，而是回退到应用侧 Ajv Draft 2020-12 完整校验。
- `scene`：可选 `general | thermodynamics | converter | blastfurnace | casting | simulation`，也接受注册表中的中文类别。
- `forced_tool`：强制模式必填，接受 `model_code / function_name / tool_uid / catalog_id`。
- `orchestration_id`：首次调用不传；收到缺参响应后原样回传，用同一编排继续未完成计划。
- 大模型负责从自然语言和对话历史提取参数；只有 Schema 声明的默认值可以自动补入。

成功或追问响应：

```json
{

  "orchestration_id": "ORCH-...",
```

## 参数失败闭环

1. 执行模型生成 function call 后，编排层使用 Ajv 8 按 JSON Schema Draft 2020-12 校验；不再维护手写关键字子集。
2. 缺失、类型错误、枚举越界、数值越界或嵌套结构错误时，工具均不执行。`required`只表示字段不存在；空字符串和空数组分别由`minLength`、`minItems`判断。Schema默认值只填充真正未提供的字段，不覆盖用户显式空值。
3. 仅由模型序列化造成的非法JSON、类型错误或多余字段允许一次受控修复，错误作为`tool`消息回传模型，状态记为`SCHEMA_REPAIR_REQUESTED`；修复不得使用用户输入、前序工具结果和Schema默认值之外的业务事实。第二次仍失败即停止。
4. 必填事实缺失、枚举不合法、范围越界和其他不能安全自动修复的问题直接改为 `needs_clarification`，`clarification.fields` 给出工具、精确嵌套字段路径、问题、期望类型和可选值。
5. `answer` 明确向用户追问，并声明不会猜测；用户补充时必须携带原 `orchestration_id`，聊天历史只用于语言上下文，不作为编排身份。
6. 若底层工具执行前置校验仍以 `INVALID_INPUT` 拒绝，按同样方式追问，不把拒绝包装为成功。
7. 两种模式都记录参数来源：用户原文、历史用户输入、Schema默认值、已执行工具结果或`unverified`，用于实验审计和猜参率统计。
8. `traditional`模式下来源记录不参与准入，只要JSON、Schema和工具业务校验通过即可执行；`evidence_enhanced`模式下不能证明来源的非默认参数以`PROVENANCE_VALIDATION_FAILED`阻断并追问。
9. 证据增强模式对嵌套对象和数组按 Schema 递归校验业务值来源；Schema 已声明的内部键名不要求用户在自然语言中逐字复述，自由键（如元素名）及其值仍必须有来源。数值来源按数值等价比较，`0.90`与`0.9`、`1×10^12`与`1e12`视为同一输入，但`100`不得匹配`1000`。
10. 已完成部分保留执行记录；补参请求携带原 `orchestration_id` 后继续原候选集、原计划和未完成步骤。
11. 实验后端的待补参编排保留 30 分钟，最多保留 500 个；当前为进程内会话存储，迁移正式产品时替换为持久化会话存储而不改变接口契约。
12. 多工具计划中，下游对象数组若是前序成功结果中某个对象数组的 Schema 投影，编排层使用完整真实数组替换模型截断副本；`upstream_execution_id`由系统绑定真实执行ID。每次替换写入`tool_calls[].dependency_bindings`，模型不再承担大数组的可靠复制。
13. G010 等元工具的`target_model_code`在每轮动态收窄为候选集中可调用的真实`model_code`；当候选中只有一个目标工具时，`base_arguments`直接继承该目标的完整输入Schema，`uncertain_parameters[].path`同步收窄为目标Schema中的数值字段路径且必须相对于`base_arguments`填写。元工具内部不确定参数的占位字段缺失或路径格式错误时，只允许模型在执行前受控修正一次，禁止用函数别名或猜测业务事实替代目标契约。
14. 工具结果归纳必须逐项覆盖用户明确请求的指标；可等价换算的计数不能替代概率等用户直接要求的结果。若进入受约束重写，重写提示继续保留这一完整性要求。数值证据直接递归读取结构化结果的数值叶子，不把序列化JSON中的数组逗号误作千位分隔符；百分数区间允许只在任一端书写百分号。

## 模型可见输入契约与 Strict 适配

- `InputField.json_schema`允许工具在不改变既有 Python 调用参数的前提下声明完整嵌套 JSON Schema。
- 每个注册工具返回`input_contract.status`和`input_contract.gaps`，用于识别仍只写了`type: object`而未说明内部结构的位置。
- D018 已为每个供氧阶段字段补齐含义与单位；D019 已明确目标数组、候选合金对象、当前成分/合金成分/元素收得率动态映射值域；D021 已明确输入与输出物流的名称、类别、质量和组成结构。
- 当前静态审计为120项`complete`、0项`underspecified_nested_schema`。默认`production`仍只按问题与场景暴露相关候选；显式`research_full`暴露冻结快照中的全量120项，以保留后续30/60/100+规模研究能力。
- 供应商 Strict 是附加约束，不代替应用侧校验。DeepSeek Strict 只在 beta 端点且结构满足其子集时启用；动态元素映射或可选字段使原生 Strict 不兼容时，接口在`tool_contract.tools[].incompatibilities`中说明原因并安全回退。

## 审计绑定

每个实际执行记录必须在 `answer_bindings` 中绑定：

- `orchestration_id`
- `execution_id` 与 `trace_id`
- `tool_uid / catalog_id / model_code / function_name`
- `tool_version`
- 完整 `parameters`
- 由前序结果自动填充的`dependency_bindings`（字段、来源步骤、来源执行ID、来源路径和绑定策略）
- 每个参数的 `parameter_sources`
- 实际 `data_sources`；无外部数据时绑定注册工具声明的公式/算法与来源版本
- 执行 `status`

实验台对每条工具执行显示四段证据：选择了什么工具、输入什么、返回什么、依据什么。

## 工具结果归纳与安全降级

1. 工具成功返回后，原始结构化结果作为受信证据回传大模型，由大模型生成面向用户的自然语言结论。
2. 编排层校验模型答案中的数值是否可由用户输入或工具结果支持；允许按照答案明确显示精度对真实结果进行四舍五入，也允许把`0～1`比例等价表示为百分数，但不允许生成中值、未绑定推导值或被篡改的数值。若发现无依据数值，原答案不得进入产品视图。
3. 首次数值校验失败时，使用相同的已验证工具结果进行一次受约束的大模型重写，成功时标记 `tool_grounded_retry`。
4. 重写稿只有局部片段含无依据数值时，删除相应分句后再次执行全篇校验；通过时标记`tool_grounded_retry_pruned`，保留其余自然语言结论。剩余文本仍不合格或模型服务不可用时，才使用可读字段摘要并标记 `readable_tool_fallback`。
5. `grounding.initial_unsupported_numeric_values` 保留首次漂移值，`grounding.synthesis_retry` 记录重写、局部清理及删除的数值，`grounding.unsupported_numeric_values` 只表示最终产品答案仍存在的漂移值。

## 前台与后台视图

- `answer`、`candidate_selection`、`plan`、`tool_calls` 和 `answer_bindings` 属于实验/审计视图。
- `product_view` 是未来正式产品消费的最小视图，只返回结论、必要追问与简要警告。
- 正式产品不得展示模式选择、候选列表、参数 JSON、工具编号、执行顺序或完整绑定文本。
- 过程隐藏不影响后台留痕；任何产品答案仍可通过编排 ID 在实验/运维后台复核。

## 测试边界
