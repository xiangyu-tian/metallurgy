# 我对 Tool Use 的理解

## 1. 核心认识

Tool Use 并不是大模型直接运行某段代码，而是大模型根据用户目标生成一份结构化的“工具调用请求”，再由 Agent 的编排层校验、调度和执行真正的工具。

```text
用户提出问题
    ↓
编排层提供可用工具信息
    ↓
大模型决定是否需要工具，并返回工具名与参数
    ↓
编排层校验参数、权限和适用范围
    ↓
编排层调用本地函数、FastAPI、MCP或远程API
    ↓
工具返回真实结果
    ↓
编排层把结果回传大模型
    ↓
大模型基于结果组织最终答案
```

因此，各层的职责可以概括为：

| 层级 | 主要职责 |
|---|---|
| 大模型 | 理解自然语言、判断是否需要工具、选择工具、提取参数、总结结果 |
| 编排层 | 管理工具、筛选候选、校验调用请求、执行工具、回传结果、记录审计信息 |
| 接口层 | 通过 FastAPI、MCP、HTTP 等方式接收结构化请求并分发到具体实现 |
| 工具层 | 接收明确参数、执行单一业务逻辑、返回结构化结果或错误 |

## 2. JSON 为什么能够“触发”工具

JSON 本身不会执行任何内容，它只是一种数据格式，相当于一张“工具调用单”。

例如，大模型可能返回：

```json
{
  "name": "temperature_conversion",
  "arguments": {
    "value": 1600,
    "source_unit": "°C",
    "target_unit": "K"
  }
}
```

如果只是把这段 JSON 保存到文件里，不会发生任何事情。真正产生执行行为的是编排层中的分发代码：

```python
tool_registry = {
    "temperature_conversion": temperature_conversion,
    "gibbs_calculation": gibbs_calculation,
}

tool_name = model_response["name"]
arguments = model_response["arguments"]
result = tool_registry[tool_name](**arguments)
```

所以完整关系不是“JSON 自动执行”，而是：

```text
JSON调用请求
+ 编排层分发逻辑
+ 已注册的工具函数
= 一次真实工具调用
```

## 3. FastAPI 在其中的作用

当工具以独立服务运行时，FastAPI 可以作为接单和分发接口：

```python
@app.post("/api/v1/tools/{tool_name}/call")
def call_tool(tool_name: str, request: ToolCallRequest):
    tool = tool_registry[tool_name]
    return tool(**request.arguments)
```

FastAPI 主要负责：

1. 根据请求方法和 URL 匹配路由；
2. 解析请求中的 JSON；
3. 使用 Schema 校验参数；
4. 找到对应的工具实现；
5. 调用工具并把结果转换成 JSON 返回。

FastAPI 不是工具本身，也不负责业务计算。它是编排层与工具实现之间的一种接口和分发方式。

## 4. 大模型如何“提交”工具调用

人与程序交互时，通常需要填写内容并点击提交。大模型没有点击按钮的动作，它完成一次符合约定格式的结构化输出，就相当于完成了提交。

```text
人类填写表单
→ 点击提交
→ 浏览器发送HTTP请求

大模型生成工具名和参数
→ 本轮生成结束
→ 模型服务返回API响应
```

例如，大模型服务可能返回：

```json
{
  "content": null,
  "tool_calls": [
    {
      "id": "call_001",
      "name": "temperature_conversion",
      "arguments": {
        "value": 1600,
        "source_unit": "°C",
        "target_unit": "K"
      }
    }
  ],
  "finish_reason": "tool_calls"
}
```

这里的 `finish_reason: tool_calls` 表示模型本轮输出已经结束，输出内容是一份工具调用申请。大模型通常不会主动请求编排层的 FastAPI；编排层先调用模型 API，然后从模型 API 的响应中取得 `tool_calls`。

```text
编排层请求模型
    ↓
模型生成结构化调用信息
    ↓
模型API返回响应
    ↓
编排层读取tool_calls
```

因此，大模型的“提交”不是主动发起一次新的网络请求，而是完成一次约定格式的输出，并由模型服务把输出返回给正在等待的编排层。

## 5. `invoke()` 之后为什么会执行工具

在普通同步程序中，这主要是程序顺序执行，不是工具自动触发。

```python
response = model.invoke(messages)

if response.tool_calls:
    execute_tools(response.tool_calls)
```

真实执行顺序是：

```text
1. 程序执行model.invoke(messages)
2. 程序在这一行等待模型服务响应
3. 模型服务完成推理并返回数据
4. SDK将返回数据解析为response对象
5. invoke()结束并返回response
6. Python继续执行下一行
7. if检查response.tool_calls是否为空
8. 条件成立后，编排层显式执行工具
```

所以准确描述是：

> 程序根据执行时序运行到 `if`，再根据模型响应内容决定进入工具执行分支还是最终回答分支。

一个最小的 Agent 编排循环如下：

```python
def run_agent(user_message):
    messages = [{"role": "user", "content": user_message}]

    while True:
        response = model.invoke(messages)

        if response.tool_calls:
            messages.append(response)
            results = execute_tools(response.tool_calls)
            messages.extend(results)
            continue

        return response.content
```

第一次模型输出工具调用时，只代表“本轮模型输出完成”，不代表“整个用户任务完成”。编排层执行工具并回传结果后，模型还需要再次生成最终答案。

```text
模型本轮输出完成
    ↓
编排层判断输出类型
    ├─ tool_calls：执行工具并继续循环
    ├─ 参数不足：追问用户并暂停
    ├─ final_answer：返回用户并结束
    └─ 错误或超限：停止并报告
```

异步调用的逻辑相同：

```python
response = await model.ainvoke(messages)

if response.tool_calls:
    await execute_tools(response.tool_calls)
```

`await` 会在等待模型响应时暂时让出执行权，响应到达后仍然从下一行继续。流式调用则通过循环或回调持续接收片段，等到结束事件后再组装并检查完整的工具调用。这种情况形式上更像事件触发，但事件处理规则仍然是编排程序预先写好的。

## 6. 工具本身没有自然语言触发条件

工具是被动能力，只负责：

```text
接收参数 → 执行业务逻辑 → 返回结果
```

“是否需要调用工具”和“应该调用哪个工具”的触发判断发生在编排层，而不是工具内部。最简单的编排逻辑类似于 `switch`：

```python
if intent == "temperature_conversion":
    result = temperature_tool(arguments)
elif intent == "gibbs_calculation":
    result = gibbs_tool(arguments)
```

工具较多时，一般使用动态注册表替代大量硬编码分支：

```python
tool = tool_registry[selected_tool_name]
result = tool(**arguments)
```

因此需要区分：

- 是否调用、选择哪个工具：由编排层决定；
- 参数是否满足执行要求：由 Schema 和校验规则决定；
- 实际业务计算：由工具函数完成。

工具名称、描述和适用场景不是工具自身的触发器，而是编排层或大模型筛选工具时使用的信息。

## 7. LangChain 中 `@tool` 的含义

在 LangChain 中，`@tool` 会把普通 Python 函数包装成 LangChain 能识别的工具对象，并提取工具名称、说明、参数 Schema 和实际执行入口。

```python
from langchain.tools import tool
from langchain.agents import create_agent

@tool
def temperature_conversion(celsius: float) -> float:
    """将摄氏温度换算为开尔文。"""
    return celsius + 273.15

agent = create_agent(
    model="模型名称",
    tools=[temperature_conversion],
)
```

这里：

- `@tool` 相当于给函数制作工具身份证和参数说明书；
- `tools=[temperature_conversion]` 才是把工具加入这个 Agent 的可用工具集合；
- Agent 运行时负责读取模型生成的调用请求并执行对应函数。

## 8. 工具调用与运行环境的关系

工具的调用契约可以与运行环境解耦，但工具能否真正运行，仍依赖具体环境。

同一个工具可以通过不同方式调用：

```text
同一进程：函数调用或 tool.invoke(arguments)
HTTP服务：POST /tools/{name}/call
MCP服务：call_tool(name, arguments)
消息队列：发送任务并等待结果
命令行：启动子进程，通过stdin/stdout传递信息
```

只要核心逻辑和接口契约不变，工具可以迁移到其他环境。但是新环境仍需具备：

- 兼容的语言运行时和依赖版本；
- 所需数据库、模型文件和数据资源；
- 网络、API密钥和访问权限；
- 一致的输入输出协议；
- 必要的硬件与系统能力。

因此更准确的结论是：

> 工具的选择和调用意图可以与运行环境无关；工具实现仍然依赖环境。迁移环境时，主要需要适配信息传递方式、依赖和外部资源。

## 9. 一个完整 Tool 应该定义什么

工具本身不需要定义“自然语言触发条件”，但应提供完整、稳定的使用契约：

- 工具名称和功能描述；
- 明确且单一的业务能力；
- 输入参数及 JSON Schema；
- 必填字段、单位、枚举和适用范围；
- 拒绝执行的条件与错误码；
- 结构化输出格式；
- 工具版本、执行 ID 和数据来源。

编排层则需要定义：

- 什么时候允许使用工具；
- 如何从全部工具中筛选候选；
- 使用强制调用、自动选择还是多工具规划；
- 参数不足时如何向用户追问；
- 如何执行、重试、终止和回传结果；
- 如何保存完整调用证据。

## 10. 理解 Tool Use 所需的 Python 基础

理解 Tool Use 不需要先学完全部 Python。优先掌握以下内容即可：

```text
变量与数据类型
→ 函数、参数和返回值
→ 字典与列表
→ if / for / while
→ 异常处理
→ 类
→ 装饰器
→ HTTP与FastAPI
→ async / await
→ Agent编排循环
```

其中最关键的是理解：

```python
response = model.invoke(messages)

if response.tool_calls:
    results = execute_tools(response.tool_calls)
else:
    return response.content
```

能逐行解释这段代码，就已经掌握了 Agent Tool Use 的主要运行机制。

## 11. 最终总结

我对 Tool Use 的最终理解是：

> Tool 是一个被动、可调用、具有明确输入输出契约的能力单元；大模型负责理解和提出调用请求，编排层负责决定是否调用、选择工具、校验参数并完成真实执行，FastAPI、MCP 或函数调用只是编排层连接工具的不同方式。

也可以进一步简化为：

```text
模型负责想
编排层负责调度
接口负责传递
工具负责执行
```
